# Инструкция для школы

Эта инструкция предназначена для учителей, администратора школы и сотрудника, который обслуживает компьютер-сервер.

## Как учителю работать с платформой

1. Откройте адрес платформы в браузере. В школьной сети его сообщает сотрудник, который установил систему. Если школа настроила внешний доступ, используйте выданный школе HTTPS-адрес.
2. Ученики входят по общему коду школы и вводят имя с фамилией. Преподаватели входят по личным email и паролю.
3. В разделе заданий создайте работу: выберите предмет, укажите название, затем добавьте вопросы и варианты ответа. Поддерживаются вопросы с одним ответом, несколькими ответами и текстом.
4. Опубликуйте задание, когда оно готово. Ученики увидят опубликованные работы после входа по общему коду.
5. В разделе результатов смотрите ответы, баллы и диаграммы. Текстовые ответы оцениваются вручную: откройте работу и укажите балл, который считаете справедливым.

Предмет, формулировки вопросов, варианты и баллы задаются при создании задания. В текущей версии уже сохранённое задание нельзя отредактировать: если нашли ошибку, создайте новую работу с исправлениями. README и исходный код для обычной работы менять не нужно.

## Что делает администратор

- Создаёт личные аккаунты преподавателей в разделе **«Аккаунты»**: имя, фамилия, email и пароль.
- Задаёт или меняет общий код входа учеников в разделе **«Аккаунты»**. Ученики вводят код, имя и фамилию; личные аккаунты им не нужны.
- Передаёт преподавателям email и пароль, ученикам — общий код. Для аккаунтов сотрудников нужен пароль не короче 12 символов.
- Создаёт задания и управляет доступом к ним.
- Преподаватели и администратор создают и проверяют тесты. Удалять тесты вместе с попытками и результатами может только администратор.
- Не пересылает файл `.env`, пароль базы данных и Cloudflare Tunnel Token: это технические секреты сервера.

## Установка на компьютер школы

Компьютер-сервер должен быть включён, подключён к интернету и доступен в школьной сети. На нём хранится общая база; остальные пользователи открывают платформу в браузере. Установку нужно запускать в той же учётной записи Windows, под которой сервер будет работать постоянно.

1. Запустите полученный файл установщика `ZailyUrpaqSetup.exe`, подтвердите запрос Windows на права администратора и заполните поля в окне установщика.
2. Если Docker Desktop ещё не установлен, установщик скачает его с официального сайта и проверит цифровую подпись. При первом запуске Docker примите лицензионное соглашение в его окне.
3. Оставьте `C:\ZailyUrpaq` или выберите место на диске: установщик создаст внутри отдельную папку `ZailyUrpaq` и поместит файлы туда. Если выбрать саму папку `ZailyUrpaq`, второй уровень не добавляется.
4. При первой установке укажите имя, фамилию, email и пароль первого администратора, а также общий код учеников. Сохраните пароль и код для дальнейшего входа.
5. При необходимости снимите галочку создания ярлыка на рабочем столе. Дождитесь загрузки компонентов и запуска платформы. Установщик покажет адреса для сервера и школьной сети и откроет сайт.
6. Попросите сетевого администратора закрепить IP-адрес за компьютером-сервером. С других компьютеров зайдите по защищённому адресу из установщика, например `https://192.168.1.20:8443`. Перед первым входом установите доверие к сертификату школы по инструкции ниже.

Для первой установки нужны интернет, 64-разрядная Windows 10 версии 22H2 (сборка 19045) или Windows 11 версии 23H2 (сборка 22631) либо новее, аппаратная виртуализация, WSL 2 версии 2.1.5+ и не менее 8 ГБ RAM. Установщик проверяет версию Windows до загрузки компонентов. Внимание: стандартная поддержка Windows 10 завершилась 14 октября 2025 года; на таком компьютере должны оставаться действующими обновления безопасности для конкретного выпуска. Для нового школьного сервера предпочтительна поддерживаемая версия Windows 11. Если Windows попросит перезагрузку для включения WSL, перезагрузите компьютер и запустите `ZailyUrpaqSetup.exe` ещё раз. Docker Desktop при первом запуске попросит принять лицензию; установщик не принимает её автоматически. Первый запуск может занять несколько минут, пока загружаются образы приложения и базы данных.

В браузере компьютера-сервера платформа открывается по адресу `http://localhost:8080`. Если компьютер выключен или пользователь сервера не вошёл в Windows, сайт временно недоступен. При входе пользователя Docker Desktop запускается автоматически, затем запускается сервер.

Если Docker или сервер закрыли вручную, дважды щёлкните ярлык **Zialy Urpaq** на рабочем столе. Он запустит Docker, дождётся готовности сервера и откроет сайт в браузере на странице входа. Сам ярлык не запускает повторную установку и не показывает консоль PowerShell.

## Защищённый адрес внутри школы

Сайт работает только в школьной сети по адресу `https://<IP сервера>:8443`. После установки файл `lan-root-ca.crt` находится в папке платформы. Это открытый корневой сертификат именно этого сервера; приватный ключ остаётся в сохраняемом Docker-томе Caddy. На компьютере-сервере установщик добавляет сертификат в хранилище текущего пользователя Windows.

Сетевой администратор школы должен один раз установить **только этот** `lan-root-ca.crt` в доверенные корневые центры сертификации каждого школьного устройства, которому нужен сайт. На Windows: открыть сертификат → «Установить сертификат» → «Текущий пользователь» → «Поместить все сертификаты в следующее хранилище» → «Доверенные корневые центры сертификации». На управляемых телефонах распространить тот же сертификат через средства управления устройствами; на iPhone после установки профиля отдельно включить полное доверие в настройках сертификатов, на Android проверить требования конкретной версии и браузера. Устанавливать корневой сертификат следует только на школьные устройства после сверки файла с администратором: доверие к чужому корневому сертификату даёт ему широкие полномочия. Если браузер показывает ошибку сертификата, нельзя обходить её кнопкой «Продолжить»; проверьте IP, дату и доверие к сертификату.

IP-адрес компьютера-сервера должен оставаться постоянным. Если он изменится, администратору нужно обновить `SCHOOL_LAN_IP` и `LIVEKIT_NODE_IP` в `.env`, указать новый `wss://<новый IP>:8443/livekit` в `LIVEKIT_PUBLIC_URL`, затем перезапустить платформу ярлыком. После выпуска сертификата для нового IP нужно заново проверить HTTPS и экранную трансляцию. Для работы учеников и преподавателей вне школьной сети этот вариант не предназначен.

В Windows Firewall для профиля **Private** установщик открывает TCP 8443 для сайта и TCP 7881 / UDP 7882 для видео только из `LocalSubnet`. TCP 8080 остаётся доступен локальной подсети для совместимости и проверки сервера; ученикам и преподавателям выдавайте только HTTPS-адрес. Трансляция экрана требует защищённого адреса и поддержки браузера; поддержку каждого школьного телефона надо проверить отдельно.

## Доступ из дома через Cloudflare (необязательно)

Для внешнего доступа школе нужны собственный домен в Cloudflare и созданный там Tunnel. Сотрудник, который настраивает сеть:

1. Создаёт Tunnel в аккаунте Cloudflare и добавляет публичное имя сайта на домене школы.
2. Указывает для него внутренний сервис `http://caddy:80` и ждёт статуса **Healthy**.
3. На компьютере-сервере открывает ярлык **Zialy Urpaq - Cloudflare**, вводит этот публичный hostname и вставляет Tunnel Token в графическое окно. PowerShell-консоль открывать не нужно.

Token сохраняется в `.env` с ограниченными правами Windows. Он даёт возможность запускать Tunnel, поэтому не отправляйте его в чат и не добавляйте в GitHub. Настройка также переключает LiveKit signaling на `wss://<hostname>/livekit`, чтобы HTTPS-страница могла подключиться без браузерной блокировки незашифрованного WebSocket. После запуска приложение проверит ответы платформы на `https://<hostname>/api/health` и `https://<hostname>/livekit/`; если проверка не пройдёт, Tunnel мог запуститься, но публичный адрес ещё не считается готовым. Исправьте Tunnel/Public Hostname в панели Cloudflare и повторите настройку. Передачу видео дополнительно проверьте с устройства ученика в школьной сети.

Видеопоток идёт напрямую на LAN IP компьютера-сервера. Для учеников вне школы потребуется отдельно развернуть и проверить публично достижимый LiveKit/TURN маршрут: HTTPS-сайт через Tunnel сам по себе не делает видеопоток доступным из интернета. В текущем школьном варианте внешний доступ не настраивается.

## Обновление и восстановление базы

При повторном запуске установщика существующие тома Docker должны сохраняться. В платформе используются две независимые базы PostgreSQL: основная `schoolcrm` и архив результатов `schoolresults`. Установщик синхронизирует пароль роли `schoolcrm` в обеих базах; API запускается после того, как обе базы проходят healthcheck. Это помогает избежать ситуации, когда обновление пароля основной базы проходит успешно, а фоновая доставка результатов остаётся с устаревшими учётными данными.

Перед обновлением:
1. Запустите `packaging\windows\Backup.ps1` и убедитесь, что обе резервные копии созданы и для них выведены SHA256.
2. Скопируйте обе копии на отдельный зашифрованный носитель или в контролируемое хранилище, не на тот же диск сервера.
3. После обновления проверьте вход учителя и ученика, откройте старый результат и убедитесь, что в разделе результатов присутствуют ранее завершённые попытки.
4. Не удаляйте Docker volumes `school_data` и `results_data` при обновлении. Команды с `down -v` удаляют данные и не должны использоваться для обычного обновления.

Проверка `pg_restore --list` подтверждает, что дамп читается как архив PostgreSQL, но не заменяет полноценное восстановление. Периодически выполняйте восстановление в отдельные тестовые базы и проверяйте вход и известные результаты до того, как считать резервную копию пригодной для аварийного восстановления.

В CI также запускается отдельная проверка восстановления обеих PostgreSQL-баз: тестовые дампы создаются через PostgreSQL 17, восстанавливаются в новые базы с суффиксом `test`, после чего сравниваются контрольные записи. Этот автоматический тест не читает школьные данные и не заменяет периодическое восстановление ваших реальных резервных копий на отдельном компьютере.

## Резервные копии

Резервное копирование выполняет сотрудник, отвечающий за сервер:

1. Запустите PowerShell от имени пользователя сервера.
2. Выполните файл `C:\ZailyUrpaq\packaging\windows\Backup.ps1` (если установка была в другую папку — замените путь).
3. Скопируйте оба файла одного запуска из папки `backups`: `zailyurpaq-<дата-время>.dump` и `zailyurpaq-results-<дата-время>.dump` на отдельный защищённый диск или в хранилище школы.

Скрипт сохраняет две копии: основную базу платформы и отдельную базу результатов. Перед копированием на компьютер он проверяет каждый дамп командой `pg_restore --list`, проверяет, что скопированный файл существует и не пуст, а в конце печатает SHA256 обоих файлов. При любой ошибке скрипт завершается с ошибкой вместо сообщения об успешном завершении. Копия на том же компьютере не защитит от поломки или потери этого компьютера.

После копирования сравните SHA256 исходных файлов и файлов на отдельном носителе командой `Get-FileHash -Algorithm SHA256 <путь-к-файлу>`. Храните резервные копии ученических данных в зашифрованном школьном хранилище с ограниченным доступом. Ответственного, место хранения и график необходимо вписать в акт приёмки; место вне сервера должен назначить администратор школы.

### Проверка восстановления

Восстановление сначала проверяют в **новых отдельных томах**, сохраняя действующие базы. Не запускайте `pg_restore --clean` на школьной базе и не выполняйте `docker compose down -v` в школьной установке.

1. Создайте отдельный Compose-проект с двумя новыми PostgreSQL-томами и отдельным API; не публикуйте его на портах действующей установки.
2. Перед восстановлением проверьте оба дампа через `pg_restore --list`. Для проверки используйте ту же основную версию PostgreSQL, что создала копию.
3. Скопируйте каждый дамп в соответствующий **тестовый** контейнер и восстановите через `pg_restore --exit-on-error --no-owner -U schoolcrm -d <новая_тестовая_БД> <файл.dump>`.
4. Сверьте количество пользователей, тестов, комнат, участников, попыток, ответов, outbox и экспортированных результатов. Запустите API с адресами восстановленных баз, войдите существующей учётной записью и откройте известный результат комнаты.
5. Только после успешной проверки составьте отдельный план переключения школьной установки с сохранением исходных томов. Зафиксируйте ответственного и результат проверки.

Для разработчика подготовлена воспроизводимая проверка **только одноразового стенда** `zaily-lancheck-20261019`: `node apps/api/test/qa-backup-recovery.mjs`. Она запускает неизменённый `Backup.ps1`, сверяет данные после восстановления, проверяет вход и аналитику через API, запускает PostgreSQL-интеграционные тесты и удаляет только созданные ею ресурсы с проверкой меток владельца. Дампы, SHA256 и отчёт остаются в исключённой из репозитория папке `tmp/recovery-20261019`. Это не команда восстановления рабочей школы.

### Быстрая проверка установленного сервера

Перед ручными испытаниями выполните безопасную read-only проверку HTTPS и состояния баз. Она не создаёт учётных записей, не меняет данные и не отключает проверку TLS. Запускайте её с компьютера, который доверяет корневому сертификату сервера:

```powershell
$env:QA_BASE_URL = 'https://192.168.1.20:8443'
$env:QA_CA_FILE = 'C:\path\to\lan-root-ca.crt'
node apps/api/test/qa-release-smoke.mjs
```

Замените IP и путь на значения тестируемой установки. Проверка принимает только localhost или частный/link-local IPv4, требует доверенный сертификат, успешный `/api/health`, подключённую основную базу и доставку результатов в состоянии `connected` с нулевой очередью. При ошибке или непустой очереди сценарий завершается с ошибкой. Скрипт явно выводит, что реальное медиа, восстановление Wi-Fi и восстановление резервной копии им не проверены. Не копируйте приватные ключи и секреты в репозиторий; для `QA_CA_FILE` используйте только публичный корневой сертификат.

### Приёмочная проверка производительности и сети

Автоматические проверки в GitHub не подключаются к компьютеру школы и не проверяют физические телефоны. Перед запуском нагрузочного сценария подготовьте **отдельный одноразовый стенд** на локальном адресе `127.0.0.1:18081`, с отдельными томами и тестовой БД. Никогда не запускайте нагрузочный сценарий против школьного адреса или рабочей базы: он создаёт администратора, задание, 10 комнат и до 400 участников.

В PowerShell задайте адрес стенда и тестовые секреты, затем запустите:

```powershell
$env:LOAD_BASE_URL = 'http://127.0.0.1:18081'
$env:LOAD_BOOTSTRAP_KEY = '<одноразовый ключ только для тестового стенда>'
$env:LOAD_ADMIN_PASSWORD = '<одноразовый пароль только для тестового стенда>'
node apps/api/test/qa-room-load.mjs
```

Сценарий выводит число успешных запросов и задержки по фазам: создание комнат, подключение, чтение, автосохранение, отправка и проверка состава комнат. Он должен завершиться сообщением `result: passed`; это проверка серверного пути под нагрузкой, а не гарантия работы на любой школьной сети.

Для LAN-приёмки используйте только отдельную установку с её тестовым `test.env` и публичным корневым сертификатом. `qa-lan-acceptance.mjs` проверяет вход в комнату, раздельные сессии одинаковых ФИО, восстановление сохранённых ответов, повторную отправку и аналитику. `qa-lan-signaling.mjs` отдельно проверяет доверие TLS и WebSocket-сигнализацию LiveKit. Успешный WebSocket handshake **не доказывает**, что медиапоток и захват экрана работают в браузере.

Перед передачей школе ответственный должен вручную отметить в акте:
- чистую установку на поддерживаемой версии Windows и запуск после перезагрузки;
- доступ к HTTPS с отдельного школьного компьютера после установки доверенного сертификата;
- вход учителя и ученика на целевых браузерах и устройствах;
- реальную трансляцию экрана и звук/видео, если они входят в сценарий школы;
- отключение Wi-Fi во время теста, возврат сети и восстановление ответа/таймера;
- обновление приложения без удаления томов и потери данных;
- создание обеих резервных копий на отдельном носителе и восстановление в новых изолированных томах с проверкой входа и результатов.

Если у школы нет отдельного тестового стенда или реальных целевых устройств, соответствующий пункт отмечается «не проверен», а не «успешно». Не проводите разрушительные тесты на рабочей базе.

## Обновление программы

Учителя меняют задания и оценки через интерфейс. Обновление самой платформы — отдельная техническая операция для сотрудника, который сопровождает сервер:

1. Сначала создайте резервную копию базы.
2. Получите новую версию проекта и сохраните текущий файл `.env`.
3. Замените файлы программы в папке установки, не удаляя Docker-том `school_data`.
4. В PowerShell из папки установки выполните:

   ```powershell
   $composeProject = (Get-Content .compose-project -Raw).Trim()
   docker compose -p $composeProject -f compose.production.yaml up -d --build
   ```

   При запуске API применит миграции базы данных.
5. Проверьте вход администратора, создание задания и доступ с другого компьютера.

**Не удаляйте Docker-том `school_data`:** в нём находятся аккаунты, задания и результаты учеников. Удаление папки программы само по себе не создаёт резервную копию базы.

## Если сайт не открывается

На компьютере-сервере откройте PowerShell, перейдите в папку установки и выполните:

```powershell
$composeProject = (Get-Content .compose-project -Raw).Trim()
docker compose -p $composeProject -f compose.production.yaml ps
docker compose -p $composeProject -f compose.production.yaml logs --tail 200
```

Проверьте, что Docker Desktop запущен, компьютер подключён к сети, а браузер использует правильный адрес. Если проблема остаётся, передайте сотруднику поддержки вывод этих команд, предварительно убедившись, что в нём нет секретов.

## Разработка и сборка установщика

Этот раздел нужен разработчику, который собирает новую версию `.exe`. На компьютере сборки нужны Windows, PowerShell и .NET Framework 4.x (он входит в Windows). Из корневой папки проекта выполните:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\packaging\windows\Build-Installer.ps1
```

Готовый файл появится в `packaging\windows\dist\ZailyUrpaqSetup.exe`. Установщик не включает `.env` и другие секреты. При установке на школьном компьютере Docker скачает образы и зависимости; для первой установки нужен интернет, а сборка может занять несколько минут.
